## 1. 任务 A：训练档案（纵向追踪）

### 1.1 数据流

主视频分析完成（`js/app.js` 的 `runReport()`）→ 用 `makeRecord()` 生成一条记录 → `addRecord()` 存下 → 报告里显示「较上次」对比 → 第 6 步档案区渲染。

融合报告（`generateFusion()`）也要存档，`source` 字段标成"多角度融合"。

记录结构（`makeRecord` 已定好，不要改字段名）：
```
{ id, ts, date, type, view, source, score, grade, cycleCount, metrics: { [指标id]: {num, value, unit, verdict, name} } }
```

### 1.2 报告内的「较上次」对比（`js/report.js`）

- `renderReport(el, report, opts)` 增加 `opts.compare`：一个 `{ [指标id]: {prev, delta, better, count} }` 映射，由 app.js 用 `compareMetric(records, id, num)` 算好传入。
- 每条指标行在数值下方加一个**极小的趋势标记**：有历史且 `delta != 0` 时显示 `↑ 比上次 +3.2` / `↓ 比上次 -1.1`，
  颜色按"变好/变差"（`better` 字段）决定，而不是按数值增减——`lowerIsBetter` 的指标（头部晃动、重心横移、腿臂分离时差）方向相反。
- 报告头部（分数环旁）显示一句总览，例如「较上次 +4 分 · 近 3 次均分 82（此前 76）」。
  分数比较只在**同一投篮类型 + 同一来源**之间做，类型不同就只显示历史次数，不显示分数差。
- 趋势参考型指标（`TREND_ONLY`）也要参与对比，但要标注「（趋势）」。

### 1.3 第 6 步：训练档案区（`index.html` + `js/app.js` + `css/style.css`）

新增 `<section id="step-history" class="card">`，放在第 5 步「动作对比」之后。

内容与交互：
1. **总览条**：累计分析次数、平均分、最近分数、最近 3 次均分 vs 之前 3 次均分的走向（用 `summarize()`）。
2. **评分历史曲线**：`lineChart` 画每次分析的得分折线，x 轴是日期，y 轴 0–100，背景加 60/80 分参考带。
3. **单指标趋势**：一个 `<select>` 列出所有出现过至少一次的指标（名字取 `METRIC_NAMES`），
   选中后画该指标的 `metricSeries()` 折线，**背景画该指标的 good 区间带**（`lo`–`hi`，来源见下），
   并在图上标注最近一次的值。
   good 区间的来源：指标对象里已有 `lo`/`hi`，但档案里的历史记录只存了 `num`——
   所以要在 `makeRecord` 里**额外存一份区间**（在记录的 metrics 项里加 `lo`/`hi` 字段），趋势图才能画带。
4. **记录列表**：每行显示日期、投篮类型、来源、分数、评级；展开可看该次每项指标的读数；每行有删除按钮。
5. **导出 / 导入 / 清空**三个按钮：
   - 导出：下载 `shot-analyzer-档案-<日期>.json`（用 Blob + `URL.createObjectURL`，不联网）。
   - 导入：`<input type="file">` 读文本 → `importText()` → 刷新界面；失败要提示原因（`importText` 会返回 `{ok, error}`）。
   - 清空：二次确认（`confirm()`）后 `clearRecords()`。
6. 空档案时给一句引导："还没有记录。完成一次分析后会自动存入档案。"

### 1.4 隐私与降级

- localStorage 不可用（隐私模式）时，`addRecord` 静默失败，**主流程不能因此报错**；
  档案区显示"当前浏览器无法保存档案（隐私模式或存储已满），可用导出/导入在其他设备查看"。
- 记录条数上限 200（`history.js` 里已有 `MAX_RECORDS`）。

## 3. 任务 C：场景拓宽（本任务风险最高，必须打上实验性标记）

### 3.1 现状与难点

现在 `detectAllCycles` 里的**站姿基线**假设投篮者在原地站定：
站姿帧取「上一球顶点 0.3 秒后 ~ 本次下蹲前」最直的一帧，所有高度/位移类指标都相对它归一化。
移动出手（后撤步、跳步）时这个前提不成立——投篮者一边位移一边出手，站姿帧可能根本不存在。

### 3.2 要实现的三种场景

| 场景 id | 名称 | 判定依据（可实现的量化规则） |
|---|---|---|
| `spot` | 定点站投 | 出手前 1.0s 内，双脚中点的水平位移 < 0.15×身高，且髋部垂直速度平稳 |
| `moving` | 移动后出手 | 出手前 1.0s 内双足中点水平位移 ≥ 0.15×身高（后撤步/横移/跳步） |
| `catch` | 接球即投 | 举球点到出手 < 0.25s，且这段区间内膝角变化 < 10°（没有下蹲蓄力） |

**规则必须集中在一个模块里**（新建 `js/scene.js`），便于后续调参：
- 导出 `export function classifyScene(frames, cycle, sideName, fps)` → `{ scene: "spot"|"moving"|"catch", confidence: 0–1, reason: "中文一句话" }`
- 阈值写成文件顶部的常量并写清出处注释。
- 判定要**保守**：证据不足时一律回退 `spot` 并在 `reason` 里说明"未能确认移动/接球特征，按定点站投处理"。
- `confidence` 低的时候（比如 0.4–0.6），报告里要写"场景判定不确定"。

### 3.3 动态基线改造（关键）

`detectAllCycles` 需要在检测到移动场景时给出不同的基线：
- 新增：站姿帧的选取从"最直的一帧"改为"**下蹲前 1.5s 窗口内膝角最大的那一帧**"（更贴近"蹬伸前的最高支撑点"）。
- 保持原有行为为默认，只有在 `moving` 场景下才切换。
- 周期对象上加 `scene` 字段（`"spot"` / `"moving"` / `"catch"`），并在 `js/metrics.js` 里被 `computeMetrics` 读到：
  `moving` 场景下，`balance`（重心横移）的分母改用**出手前 0.5s 的平均髋位**而不是站姿帧髋位，
  否则移动中的横移会被算成"重心不稳"，把正常移动误判成错误。

### 3.4 场景专属的新指标

| id | 名称 | 单位 | 计分 | 场景 | 口径 |
|---|---|---|---|---|---|
| `moveDist` | 出手前移动距离 | ×身高 | moving 才产出 | moving | 出手前 1.0s 双足中点的水平位移 |
| `moveSpeed` | 出手前移动速度 | ×身高/s | moving 才产出 | moving | 上述位移 / 1.0s |
| `takeoffTiming` | 起跳-出手时序 | ms | moving/spot 起跳类 | — | 从髋部开始持续上升（离地）到出手帧的间隔 |
| `dipAmount` | 沉球量 | ° | catch 才产出 | catch | 举球点之前腕部/肘角的最低点与举球点的角度差，衡量"接球后往下压了多少" |

新增指标必须同时：
- 加进 `METRIC_NAMES` 与 `METRIC_VIEWS`（`moveDist`/`moveSpeed` → `["side"]`；`takeoffTiming` → `["side","front"]`；`dipAmount` → `["side"]`），
  **否则 `mergeCycles` 会把它们丢掉**（它按 `METRIC_VIEWS` 的键遍历）。
- 给出 good 区间与建议文案；没有文献锚点的（`moveDist`、`moveSpeed`、`takeoffTiming`、`dipAmount`）
  一律设成**趋势参考型**（`verdictOverride: "info"`），并在 `TREND_ONLY` 里登记。
- 在报告里**只在该场景成立时展示**，不要在定点站投的报告里塞"移动距离 0.00×身高"这种无意义项。

### 3.5 UI

- 第 2 步的「投篮类型」下拉框旁边加一个「场景」下拉框：`自动识别` / `定点站投` / `移动后出手` / `接球即投`。
  默认"自动识别"，玩家可以手动改（机位判别已经有手动覆盖的先例，照它的样式做）。
- 报告头部显示场景判定结果 + 理由，例如「场景：移动后出手（出手前 1.0s 横向位移 0.42×身高）· 判定把握 0.8」。
- **凡是 moving/catch 场景的判定结果，报告底部都要加醒目提示**：
  「⚠️ 移动/接球场景判定为实验性功能，指标区间尚未用真实素材校准，结论仅供参考。」

### 3.6 测试要求（C 专属）

## 5. 本机环境坑（务必遵守，否则会误判）

- **git 的部分子命令 stdout 会被吞**：报 `fatal: write failure on 'stdout': Bad file descriptor`。
  可靠写法：`git status 2>&1 | cat`、`git log --oneline | cat`；或把输出重定向到文件再读。
  `git diff` 的**退出码不可靠**（对不同文件也返回 0），判断"有没有改动"要看输出内容，不要看 `$?`。
- 校验文件内容用 `sha256sum`、`cmp`、`wc`、`git cat-file`，**不要**用 `diff` 的退出码。
- 本机 `python` 是 WindowsApps 的**假壳**（一跑就退出码 49），**用 `node` 写测试脚本**。
- 曾经出现过"文件内容振荡"（好版本和坏版本之间跳变），怀疑同步盘/杀毒软件在动文件。
  多代理并行操作本仓库前，先 `find . -mmin -5 -type f` 查有没有人在并发写。
- 提交前先 `git status | cat` 确认工作区干净，别把临时文件（`_dump.txt` 之类）带进提交。
